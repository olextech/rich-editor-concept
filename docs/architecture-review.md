# Architecture review for embedding

The repository needs refactoring at the application boundary. The existing editing engine has useful module boundaries and does not need a rewrite. This preparation isolates the component, its styles, and its public contract. It preserves canonical HTML, pagination algorithms, validation, and backend PDF generation from saved template and document IDs.

## Review coverage

The review covered the frontend composition roots, component library, editor hooks, CKEditor configuration and plugins, pagination and navigation modules, HTML contract and shared styles, backend API and services, database and schemas, browser and backend tests, build configuration, README, and specifications.

## Public module boundary

The public entry exposes `DocumentEditor`, `DEFAULT_PAGE_SETTINGS`, `validatePageSettings`, and their TypeScript types. The stylesheet is a separate package export. React and ReactDOM are host-supplied peer dependencies. CKEditor uses the exact supported peer version. UI dependencies remain an internal implementation detail; the host does not need Tailwind.

The component owns one edit session. The host supplies initial HTML and changes `documentKey` to load another document or revision. Page settings and read-only state can change without recreating the editor. Canonical HTML leaves through `onChange`; readiness, layout errors, and page count leave through `onStateChange`. No API endpoint, business record, local-storage key, or sample template is required by the component. A separate optional `rich-editor-concept/client` entry supplies the HTTP client and browser output helpers without adding demo persistence to the core entry.

The package remains private. The integration path is a built local tarball, not public registry publication. See [the embedding guide](embedding.md) for installation and host responsibilities.

## Follow-up work before production integration

1. **Business data and access control.** The backend demo has no authentication or tenant isolation. Use the injectable document lookup to connect the host repository and apply the host's permissions to templates and documents. Keep business data out of the PDF request body.
2. **Storage and concurrent saves.** Decide whether to reuse the demo SQLite service or the larger application's storage. Add migrations where required. The existing update API does not detect concurrent editing conflicts; use a version or revision check if multiple users can edit a template.
3. **Host draft lifecycle.** Namespace browser drafts by user, tenant, and template where applicable. Cancel host requests and release output resources when routes close. The demo's fixed storage key and global unload warning are not part of the public component.
4. **Rendering scale and fonts.** Keep the current synchronous renderer until measured load requires a queue. Pagination performs DOM measurements and traverses the document; measure realistic large templates before introducing caching or virtualization. Establish the document fonts used by both browser and backend. Do not promise identical page counts after variable expansion.
5. **Browser and print support.** Scoped styles depend on native `@scope`. Chrome and Edge are the supported baseline. Test the native PDF viewer and actual print dialog in deployed browser versions. Automated checks cannot establish physical print success.
6. **License decision.** Supply the CKEditor license key selected for the host application. The demo's `GPL` setting is not a license grant for an embedding product.

## Validation approach

Use existing browser tests to protect page breaks, undo, selection, table and image editing, canonical serialization, save confirmation, PDF download, and native print requests. Use backend tests to protect ID validation, persistence, variable and row rendering, PDF geometry, and resource restrictions.

Add tests at the package boundary: install or import the built artifact in a host fixture, render two independent editors, confirm that host styles remain intact, exercise resizing and visibility changes, replace documents, toggle read-only mode, and unmount during initialization. Check TypeScript declarations and server rendering separately. A passing demo build alone does not verify those integration guarantees.

## Verification results

The final browser suite passed all 51 tests, including five checks against the built editor artifact in a host page. The backend suite passed all 68 tests. All nine client adapter tests passed.

The library and demo builds passed. A local tarball passed strict TypeScript checks, a plain Vite consumer build without source aliases or Tailwind, public imports, and server rendering without browser globals. Formatting and whitespace checks passed.

Native print tests verify the returned PDF and the print request. They do not verify a system print dialog or physical printing.
